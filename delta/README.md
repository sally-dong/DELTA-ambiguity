# DELTA

Measure ambiguity in prescriptive text — laws, contracts, policies, platform
rules — as **interpretive disagreement about consequences** rather than as a
property of the words themselves.

Existing ambiguity measures look at the text: sentence length, hedging,
word-level concreteness. But a policy can sound decisive and still leave
people with incompatible ideas of what it requires, and a policy can sound
vague while everyone agrees on what it rules out. DELTA measures the thing
that matters instead: pair a policy with concrete cases, ask a diverse set of
raters whether each case is permitted, and quantify how far apart they land.

```python
from delta import compute_delta_scores

scores = compute_delta_scores("results/campus_speech")
# policy  score
#      0  0.104   <- everyone reads this one the same way
#      1  0.874   <- raters split on what it permits
```

## How the score works

For each policy, case and rater you need two judgments: *does this policy
permit this case?* and *does it prohibit it?* Asking both matters, because a
policy that is simply silent on a case draws "no" to both questions, and that
is different from a case it clearly permits.

The two answers collapse to one **revealed probability** per rater:

```
revealed = (p_permit + (1 - p_prohibit)) / 2
```

A case the policy does not address lands near 0.5 rather than at an extreme.

Across raters, one policy-case pair gets a **disagreement** score:

```
disagreement = 4 * mean * (1 - mean)
```

Read each rater's revealed probability as their probability of issuing the
verdict "permitted". Then `2 * mean * (1 - mean)` is exactly the probability
that two independently sampled verdicts conflict; the score is that
probability normalized by its maximum of one half, so it runs from 0 under
total consensus to 1 when the pooled verdict is a coin flip. It also credits
*shared* uncertainty: if every rater answers 0.5 because nobody can tell
whether the policy applies, each rater's own verdict is a coin flip, so
sampled verdicts still conflict half the time. Underdetermination is itself
a symptom of ambiguity.

By the law of total variance the score splits exactly into those two sources:

```
4*mean*(1 - mean) = 4*avg(x*(1 - x)) + 4*var(x)
                     within-rater       between-rater
```

The `within` term is self-disagreement (how undetermined individual verdicts
are); the `between` term is the extra conflict attributable to raters
differing from one another. `compute_delta_scores` reports both alongside the
score; they sum to it.

The policy's DELTA score averages the case scores over cases. 0 means total
consensus; higher (up to 1) means more contested.

**Scores are relative, not absolute.** They are only meaningful for comparing
policies evaluated against the same cases and the same raters. Do not compare
scores across runs.

## Full pipeline

Scoring assumes you already have judgments. To produce them:

**1. Describe the experiment.** In a directory, write `policies.json` as a
list of `{"candidate_id": ..., "text": ...}` and a `scenario_params.json`
(see [Experiment settings](#experiment-settings) for every key).

**2. Generate cases and raters.**

```bash
delta-generate --dir experiments/campus_speech --action all
```

Cases are generated by prompting a reasoning model with *pairs* of policies
and asking for scenarios that comply with one while violating the other. Since
policies in a set usually express similar goals, this forces the model onto
precisely the distinctions that produce interpretive disagreement.

Raters are generated as opposed pairs of stakeholder identities, then each is
expanded into a short statement of that stakeholder's values and concerns.
That expansion matters: asking a model to adopt a bare persona label and
answer yes/no yields a narrow, homogeneous response distribution.

**3. Collect judgments.**

```bash
delta-run --model gemini --dir experiments/campus_speech
```

Writes `results/campus_speech_gemini/probs.csv` with one row per
`rater x policy x case x prompt`.

**4. Score**, as above.

## Scoring

```python
compute_delta_scores(
    results_dir,
    has_negative_questions=True,
    weighting="case_range",
    output_name="delta_scores.csv",
    input_file="probs.csv",
)
```

| Setting | Default | Alternatives |
|---|---|---|
| `weighting` | `"case_range"` | `"mean"` |
| `has_negative_questions` | `True` | `False` |
| `input_file` | `"probs.csv"` | any CSV in `results_dir` |
| `output_name` | `"delta_scores.csv"` | any filename; written under `results_dir/scores/` |

### `weighting` — how case disagreement averages into a policy score

**`"case_range"` (default).** Each case is weighted by the range of its
disagreement scores across the policies in the run:

```
weight(case) = max_policies disagreement - min_policies disagreement
```

A case that every policy handles identically carries no information about
which policy is more ambiguous, so it is down-weighted toward zero. A case
that splits the policies sharply counts for more.

The consequence to watch: **those weights depend on which policies are in the
run**, so a case-range score is comparable only within a single call. Scoring
a subset of policies gives different weights and therefore different scores
than scoring the full set. Score everything you intend to compare in one call.

**`"mean"`.** Every case weighted equally. Use it when case-range weights are
not meaningful or not stable:

- Raters each see only a small number of policies, so the cross-policy range
  is estimated from very little data.
- Cases are subsampled, e.g. in convergence diagnostics — weights would be
  recomputed on each subsample, adding variance unrelated to what you are
  measuring.
- You want scores that stay comparable as policies are added or removed.

### `has_negative_questions` — prompt pairing

**`True` (default).** The run asked both framings. Even prompt indices are
the permit framing, odd indices the prohibit framing; they are paired up and
collapsed via `revealed_probability`. This is what both bundled prompt
templates produce.

**`False`.** Single-prompt runs. `prob_yes` is used directly with no pairing,
so the "policy is silent on this case" signal described above is unavailable
and such cases become indistinguishable from clearly-permitted ones.

### Using the pieces directly

The two primitives are public, for computing scores over your own subsets
(a bootstrap, a per-rater-group breakdown, a convergence sweep):

```python
from delta.scoring import revealed_probability, disagreement

revealed = revealed_probability(p_permit, p_prohibit)   # elementwise
score    = disagreement(revealed.mean())
```

For the within/between decomposition, `within = 4 * (revealed * (1 - revealed)).mean()`
and `between = score - within` (equivalently `4 * revealed.var(ddof=0)`).

## Experiment settings

`scenario_params.json`, read by `delta-generate` and `delta-run`. A complete
example, for 30 raters judging 90 generated cases:

```json
{
    "policy_topic": "use of AI by students in a humanities course",
    "question": "How should students be allowed to use AI in this course?",
    "case_format_description": "specific description of a student's actions",
    "case_example": "Example: a student uses AI to generate an essay outline, then writes the essay herself.",
    "case_per_ordered_policy_pair": 3,
    "n_policy_pairs": 30,
    "n_raters": 10,
    "rater_generation_iterations": 3,
    "rater_description_length": 5,
    "rater_pair_example": "This person is a science professor.\nThis person is a humanities professor.",
    "prompt_template": "opinion_statement",
    "positive_question": "Does the policy permit this?",
    "negative_question": "Does the policy prohibit this?"
}
```

### Required

| Key | Meaning |
|---|---|
| `policy_topic` | Domain description, interpolated into generation prompts |
| `case_format_description` | What one case should look like |
| `case_example` | A worked example case |
| `case_per_ordered_policy_pair` | Cases requested per policy pair |
| `n_raters` | Stakeholders requested per generation call |
| `rater_generation_iterations` | Number of generation calls |
| `rater_description_length` | Sentences per rater persona |
| `rater_pair_example` | An example of two opposed stakeholders |
| `prompt_template` | `opinion_statement`, `domain_judgment`, or omit for a custom function |

Total raters is `n_raters × rater_generation_iterations` — with `n_raters: 10`
and `rater_generation_iterations: 3` you get 30. Generating in several smaller
calls rather than one large one is deliberate; a single call for 30 tends to
produce a more homogeneous list.

`rater_description_length` counts the base identity plus its expansions, so
`5` means one identity sentence and four elaborations.

### Optional

| Key | Default | Effect |
|---|---|---|
| `n_top_policies_for_cases` | all policies | Seed case generation from only the first N policies. Raters still evaluate against every policy |
| `n_policy_pairs` | `20` | Ordered policy pairs to seed case generation from. Set to `null` for all `n(n-1)` |
| `pair_sampling_seed` | `42` | Seed for that sample |
| `n_sampled_cases` | — | Required by `--action sample_cases`; how many cases to keep |
| `sampling_seed` | `42` | Seed for case downsampling |

**On the pair count.** The number of ordered pairs grows as `n(n-1)`, so
enumerating them all would mean 870 generation calls for 30 policies and
264,710 for 515. `n_policy_pairs` therefore defaults to **20**, which with the
usual `case_per_ordered_policy_pair: 3` gives 60 cases — around where DELTA
rankings stabilise in practice. Raise it if your policies are especially
heterogeneous, since more pairs means the cases probe more distinctions.

If a policy set is small enough that it has fewer than 20 ordered pairs, all
of them are used. Set `n_policy_pairs` to `null` to opt into every pair
regardless of cost.

### Prompt templates

| Template | Prompts per judgment | Additional required keys |
|---|---|---|
| `opinion_statement` | 2 (positive, negative) | `question`, `positive_question`, `negative_question` |
| `domain_judgment` | 6 (3 frames × 2 polarities) | `prompt_config` with `policy_label`, `case_label`, `frames` |
| custom | your choice | none; provide `custom_prompt_fn.py` in the experiment directory |

Omitting `prompt_template` loads `prompt_fn` from `custom_prompt_fn.py` in the
experiment directory, by file path.

## Model settings

### Generation (`delta-generate`)

Defaults to a reasoning model, since case and persona quality drive everything
downstream:

| Setting | Default |
|---|---|
| model | `gpt-5` |
| `thinking` | `True`, effort `"medium"` |
| `temperature` | `1` |
| `max_output_tokens` | `10000` |

The `expanded_raters` step overrides this to `thinking: False`, effort
`"minimal"`, `max_output_tokens: 200`. It appends one short sentence per call
and runs once per rater per expansion, so reasoning is wasted budget there.

### Judgments (`delta-run --model ...`)

| `--model` | Model | Temperature | Notes |
|---|---|---|---|
| `gemini` | `gemini-2.5-flash` | 1 | `thinking_budget: 0`. Used for the paper's results |
| `gpt` | `gpt-4.1-mini` | 0 | `max_output_tokens: 4` |
| `olm` | `allenai/OLMo-2-0325-32B` | — | Local base model, needs `[local]` |
| `qwen` | `Qwen/Qwen3-30B-A3B-Base` | — | Local base model, needs `[local]` |

A lightweight non-reasoning model is the right choice here: the judgment is a
single yes/no conditioned on a persona, and the score depends on the *spread*
of answers across raters, which reasoning tends to collapse.

The two local models are base rather than instruct-tuned, so prompts get an
`"Answer:"` continuation suffix instead of a system instruction, and answers
are read off token probabilities rather than parsed from text.

Trials are fixed at one per prompt. Variation across raters, not resampling of
one rater, is what the score is built on.

## Choosing how many cases and raters

More of each costs money and returns less over time, since repeated sampling
from a model produces increasingly similar cases and personas. Pick the budget
empirically: score with the full set, then re-score on random subsets and check
the rank correlation against it. Rankings typically stabilise well before the
sampled pool is exhausted.

Use `weighting="mean"` for this diagnostic. Case-range weights are recomputed
on every subsample, which would mix weight instability into the convergence
you are trying to measure.

This establishes stability *within* a generated pool, not convergence to the
broader space of cases a model could produce.
